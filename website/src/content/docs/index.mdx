## Why Aruma

Firebase gives you excellent client SDKs and a managed backend you can't leave. Aruma keeps the first part and replaces the second.

<CardGrid>
  <Card title="Keep the official SDKs" icon="puzzle">
    Web, iOS, Android, Flutter and the Admin SDKs run in their normal production mode, with no emulator mode. You swap the configuration file, and on some platforms add one line of build configuration. For Auth, Realtime Database and Firestore on supported setups your application code stays the same. Storage on iOS uses a patched build of the Storage SDK, Flutter Storage needs one helper call (`fromArumaUrl`), and servers that verify ID tokens use Aruma's admin libraries.
  </Card>
  <Card title="Own your data" icon="seti:db">
    Run it on a cheap VPS, on your own servers, or wherever PostgreSQL runs. One binary, one database, no per-operation billing.
  </Card>
  <Card title="Open source" icon="github">
    Apache 2.0. Read the code, run the tests, send a patch.
  </Card>
  <Card title="Built to be verified" icon="approve-check">
    Behavior is checked against real Firebase and the official emulators, and the official Firebase test suites are run against Aruma.
  </Card>
</CardGrid>

## How it works

<Steps>

1. Create a project and an app from the dashboard or with `arumactl`.
2. Download the app's configuration file: `google-services.json`, `GoogleService-Info.plist`, or the Web and Flutter equivalents.
3. Put it in your app in place of the Firebase one. For Auth, Realtime Database and Firestore on supported setups, your application code does not change. Where a platform needs it, add the one build line described in [`sdk/`](https://github.com/arumadev/aruma/tree/main/sdk).

</Steps>

Every project's data is reached through its project number, directly or through a project-scoped parent such as a Realtime Database id. A CI test fails any SQL query on a project table that neither filters by project nor carries a reviewed scope annotation. Aruma does not use PostgreSQL row-level security. See [architecture](docs/architecture/#tenancy).

## Status

Aruma is pre-1.0. The latest release is [v0.3.0](docs/changelog/#v030). The Document Database is in the release candidate [v0.4.0-rc.1](docs/changelog/#v040-rc1), and some of its verification is still pending.

| Service | Status | Details |
|---|---|---|
| **Platform**: projects, apps, API keys, service accounts, dashboard, Management API | Released | [Architecture](docs/architecture/) |
| **Authentication** | Released in v0.1.0 | [Compatibility](docs/reference/compatibility/#auth) |
| **Realtime Database** | Released in v0.2.0, off by default (`ARUMA_RTDB_ENABLED`) | [Compatibility](docs/reference/compatibility/#realtime-database) |
| **Security Rules** | Released in v0.3.0 | [Compatibility](docs/reference/compatibility/#security-rules) |

| **Document Database (Firestore-compatible)** | Release candidate v0.4.0-rc.1, off by default (`ARUMA_DOCUMENTS_ENABLED`) | [Compatibility](docs/reference/compatibility/#firestore) |
| **Cloud Messaging, App Check, Remote Config, Functions** | Planned | |

Differences from Firebase that we know of are documented in [known differences](docs/reference/known-differences/).

## The console

Every Aruma server ships with a console, embedded in the same binary. Create projects and apps, manage users, edit rules, browse data and files, and download the configuration files your apps need. The console is in English and Arabic (right to left).

## Get started

```bash
make dashboard   # build the console and embed it in the binary (once)
make dev         # create .env with a random key, then the database, migrations and the server
```

Then open `http://localhost:8080`. The full steps are in the [quick start](docs/getting-started/).
