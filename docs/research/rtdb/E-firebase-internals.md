# E - Public statements about Firebase RTDB internals (research 2026-10-20)
Method: WebSearch/WebFetch only. stackoverflow.com, reddit, web.archive.org, api.stackexchange.com are NOT reachable from the tool, so Stack Overflow staff answers were NOT read (gap). V = read on the page by fetch; U = unverified/secondary.

## Headline
No Google/Firebase source says "single-threaded", "in memory", Scala, or anything about the server process model. Searches of docs, firebase-talk, HN, blog, GitHub found none. Evidence for a serialized per-database executor is indirect (V): profiler docs name "pending time" and "head-of-line blocking"; optimize doc says each write ~0.1% of utilization; limits say 1000 writes/s per DB and sharding is "the recommended remedy".

## What this implies for each Aruma decision
(Inference, not fact.)
- Q1 databaseURL shape: Firebase itself uses 3 labels for us-central1 (`NAME.firebaseio.com`) and 4 for others (`NAME.REGION.firebasedatabase.app`). Namespace is the first label in both. The SDK's own handshake host (`s-...-nss-N`) is explicitly "subject to change", shared, and not meant to be hard-coded, so Aruma can answer `h` with its own host (or the same one). Recommend documenting 4-label (`<db>.<region>.<aruma-host>`) as the ns-safe shape given the already-known iOS `?ns=` quirk; location is immutable in Firebase, so a region label is a stable identifier.
- Q2 storage: Firebase's own docs imply a persistence layer plus a server cache, whole-subtree reads, 75M-node listen cap and 256 MB read cap, but never that the DB must fit in RAM. Nothing public obliges Aruma to keep data in memory; Postgres rows (path-keyed or JSONB tree) is consistent with every documented behaviour, but subtree reads and "delete is costly with thousands of leaves" mean path-prefix indexing is needed. Do not copy the 75M figure; set a lower safe cap.
- Q3 queries without index: Firebase's documented behaviour is that the server returns the whole location plus a `no_index` warning and the client filters; REST rejects unindexed orderBy. Aruma can mirror that exactly (send all children + warning) or reject, but the SDK handles the warning gracefully; for REST reject with the Firebase-style index error. Single orderBy per query is documented without reason; replicate.
- Q4 rules scope: rules are checked on every read/write and on onDisconnect twice (registration and fire); `.read` cascades, "rules are not filters"; a listen needs read permission at the listened path; `cancel`/permission-denied on failure. No info on re-check at rule edit; Aruma should define it (recommend re-evaluate or cancel listens on rules publish) and note it as its own design choice. Rules size limit for RTDB unverified; 256 KB is a safe copy of the Firestore number.
- Q5 REST: REST is documented as a separate, connectionless path (not counted in connections, own TLS cost), 256 MB write limit, index required for orderBy, `timeout` max 15 min, SSE `auth_revoked`/`cancel`/`keep-alive` events. A minimal v0.2 REST (GET/PUT/PATCH/POST/DELETE, shallow, orderBy+index check) is consistent with docs.
- Q6 long polling: Firebase keeps it as fallback only when the last WebSocket attempt failed; node SDK has none; LP params: 25 s keepalive requests, 1870-byte URL segments, 30 s connect timeout. Server must set up `.lp` for browsers behind proxies, but there is no published share; it can be deferred to after WebSocket works unless web SDK support behind corporate proxies is a v0.2 goal.
- Q7 change log: Firebase runs a single serialized executor per database (indirect evidence: pending time, head-of-line blocking, 0.1% per write, 1000 writes/s, ~100k responses/s). A per-database monotonically increasing sequence (Aruma's `events.changes` seq) assigned inside the write transaction mirrors that model: a per-project write lock or advisory lock makes ordering trivial and loses no events. Client write ids are per-client counters and the transaction protocol sends a hash and answers `datastale`, so the server must keep a hash/compare function for the transaction put.
- Q8 default limits: Public numbers to copy as defaults (all V): 200k conns/DB (Spark 100), 1000 writes/s soft, 64 MB/min, depth 32, key 768 bytes, string 10 MB, SDK write 16 MB / REST 256 MB, read 256 MB, query 15 min, WS frame 16 KB, 25 transaction retries. Aruma's existing 1 MB body cap contradicts 16 MB SDK writes: raise for the RTDB routes, or document a lower cap. Do not copy 200k/75M; pick values Postgres can sustain and state them.
