## Q1: شكل `databaseURL`

**التوصية:** `https://<project>-default-rtdb.<rtdb_domain>`. اسم القاعدة هو أول جزء من النطاق، وليس معامل `?ns=`.

- **`rtdb_domain`** إعداد جديد. نقترح نطاقًا فرعيًا مخصصًا، مثل `rtdb.example.com`، فيصير الرابط من أربعة أجزاء كما في مناطق Firebase نفسها: `chat-default-rtdb.europe-west1.firebasedatabase.app`.
- **الخادم** يأخذ الاسم من أول جزء في `Host`. ويقبل `?ns=` للتطوير المحلي فقط، ويرفض الطلب إن اختلف الاثنان. والأسماء التي تبدأ بـ `s-` محجوزة.
- **في المصافحة** يرسل الخادم في `h` نطاقه هو.

**لماذا:** فحص كيف تقرأ كل مكتبة الرابط (F، والسطور في الكود):

| الرابط | الويب | Android | iOS | Admin Node | Admin Java | Admin Go | Admin Python | Unity/C++ |
|---|---|---|---|---|---|---|---|---|
| `chat-default-rtdb.rtdb.example.com` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `chat-default-rtdb.example.com` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `aruma.example.com/?ns=chat-default-rtdb` | ✓ | ✓ | ✗ يقرأ `aruma` | ✓ | ✓ | ✗ يكسر بناء المسار | ✗ يُسقط `?ns=` | ✗ خطأ |
| `db.aruma.example.com/?ns=…` | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ |

- ✔ iOS: `FUtilities.m:184`، `if ([parts count] == 3)` يأخذ الجزء الأول ويتجاهل `ns`.
- ✔ Admin Go: `db/db.go:125`، الرابط يُستعمل أساسًا كما هو، و`ns` يُرسل للمحاكي فقط (`:130`).
- ✔ Admin Python: `db.py:813` يأخذ `https://<netloc>` فقط، و`:836` يأخذ الاسم من أول جزء.

**الشهادة:** شهادة wildcard من Let's Encrypt تحتاج تحقق DNS-01، أي مفتاح API من مزوّد DNS. البديل الأبسط:
- **سجل DNS عام واحد** `*.rtdb.example.com` يشير إلى الخادم. سجل عادي بلا مفتاح API.
- **Caddy مع `on_demand_tls`:** يصدر شهادة لكل اسم عند أول اتصال، بتحقق HTTP-01 أو TLS-ALPN-01. ويسأل قبلها Aruma عبر `ask`: هل هذا الاسم مشروع موجود؟ إن رد بـ 2xx يصدر الشهادة. نقطة `ask` تُخدم على العنوان الخاص، لأنها تكشف هل المشروع موجود.
- **الحدود:** 50 شهادة جديدة لكل نطاق مسجّل في 7 أيام (Let's Encrypt). وحد داخلي في Caddy: 10 محاولات كل 10 ثوانٍ. وأول اتصال بكل اسم ينتظر ثواني، ومهلة اتصال المكتبات 30 ثانية.
- **خلف Cloudflare:** شهادته المجانية تغطي مستوى فرعيًا واحدًا. فالنطاق رباعي الأجزاء يكون بلا الوكيل البرتقالي (DNS only)، أو يُختار نطاق ثلاثي مثل `chat-default-rtdb.example-db.com`.

**مثال، قبل وبعد:**
- **قبل:** الصيغة المبدئية `https://aruma.example.com/?ns=chat-default-rtdb`. iOS يتصل بقاعدة اسمها `aruma`، وAdmin Go يطلب `https://aruma.example.com/?ns=chat-default-rtdb/users.json`.
- **بعد:** `https://chat-default-rtdb.rtdb.example.com`. كل المكتبات تقرأ `chat-default-rtdb`.

**التطوير المحلي:** `http://127.0.0.1:<port>/?ns=<ns>` يعمل في الويب وAndroid وiOS وJava وPython، لأن `127.0.0.1` من أربعة أجزاء. وAdmin Go يحتاج `localhost:<port>?ns=<ns>`. وUnity يحتاج اسمًا في ملف hosts.

**ما يتغيّر:** ADR-007 (صيغة `databaseURL`)، وADR-008 (المدخل الواحد يقبل النطاق الفرعي لـ RTDB)، و`tenancy/core/projects.go:50`.

## Q2: التخزين

**التوصية:** صف لكل ورقة في Postgres: `nodes(database, path text COLLATE "C", value, priority)`. قراءة الفرع استعلام نطاق على البادئة. الكاتب الواحد يجمع عدة كتابات في كل حفظ.

**الدليل:** تجربة G على Apple M1 وPostgres 18.1 بإعداداته الافتراضية. البيانات: 600 ألف ورقة، و500 غرفة، و50 ألف مستخدم.

| | صف لكل ورقة | jsonb لكل غرفة | jsonb لكل فرع رئيسي | ذاكرة مع سجل |
|---|---|---|---|---|
| كتابة ورقة (الوسيط) | 0.27 ms | 1.5 ms | 511 ms | 0.10 ms |
| كتابات/ث، كاتب واحد، 16 لكل حفظ | 43 ألفًا (15 ألفًا بدلالة «set» كاملة) | 736 | 2 | 52 ألفًا |
| قراءة غرفة (2000 رسالة) | 4.4 ms | 1.2 ms | 35 ms | 1.0 ms |
| قراءة 50 ألف مستخدم (5 MB) | 107 ms | 23 ms | 33 ms | 31 ms |
| الحجم بعد التجربة | 130 MB | 469 MB | 612 MB | سجل 507 MB، و110 MB ذاكرة |

- **حد Firebase** نحو 1000 كتابة في الثانية للقاعدة (صفحة الحدود)، والصف لكل ورقة يتجاوزه بهامش كبير.
- **jsonb** يعيد كتابة المستند كله مع كل تعديل، فيقف عند حد Firebase أو دونه ويتضخم.
- **الذاكرة** أسرع، لكنها تحتاج لقطات وضغطًا: إعادة تشغيل 3.8 مليون سطر سجل أخذت 8.5 ثوانٍ. وتحدّ القاعدة بحجم الذاكرة.
- **أين يضعف:** قراءة فرع ضخم دفعة واحدة، 107 ms لخمسين ألف ابن. نقبله في 0.2. وإن ظهر في قياس R7 تُضاف ذاكرة مؤقتة للفروع الساخنة دون تغيير التخزين.
- **حد الفهرس:** مدخل فهرس Postgres حده نحو 2.7 KB. ✔ والمكتبة نفسها تحد المسار الكامل بـ 768 بايت: `MAX_PATH_LENGTH_BYTES` في `Path.ts:26,308`، وتحسبه بكل أجزائه. فالمسار يتسع في الفهرس، ونطبّق الحد نفسه على الخادم.
- **تحفّظ على الأرقام:** القياس على macOS، حيث لا يفرض المزامنة على ذاكرة القرص. فرقم الحفظ الفردي متفائل، أما أرقام الجمع (16 فأكثر) فقلّما تتأثر.

## Q3: الاستعلامات

**التوصية:** التصفية على الخادم كما يفعل Firebase، بترتيب يُحسب عند الطلب، بلا فهرس دائم في 0.2.

| نوع الترتيب | بلا `.indexOn` | مع `.indexOn` |
|---|---|---|
| بالمفتاح، أو بالأولوية (الافتراضي) | يُصفّى على الخادم ويُوسَم دائمًا ✔ | كذلك |
| بقيمة ابن، أو بالقيمة نفسها | الاستماع: كل الأبناء مع `no_index` ✔. و`get`: خطأ `no_index` ✔. وREST: 400 «Index not defined» ✔ | يُصفّى ويُوسَم ✔ |

- ✔ تجربة `q2.mjs` على المحاكي 4.11.2 (ملحق B).
- **الدليل من الوثائق:** «Indexes are not required for development unless you are using the REST API» ([indexing-data](https://firebase.google.com/docs/database/security/indexing-data)). ورسالة المكتبة عند `no_index`: البيانات «downloaded and filtered on the client» (`PersistentConnection.ts:316-320`).
- **الكلفة (G):** آخر 50 رسالة من 2305:

  | الطريقة | الزمن | البيانات |
  |---|---|---|
  | إرسال الكل | 7.6 ms | 330 KB |
  | بفهرس | 0.25 ms | 6 KB |

  الترتيب عند الطلب ينمو بعدد الأبناء. المستمع يحفظ نافذته في الذاكرة ويُحدَّث مع كل كتابة، فلا يُعاد الاستعلام.
- **الفهرس الدائم لاحقًا:** جدول `idx(database, parent, index_key, نوع، قيمة، مفتاح)` يُحدَّث في معاملة الكتابة نفسها. ولا يصلح فهرس تعبيري في Postgres، لأنه يُعرَّف لكل اسم ابن على كل المسارات، ويفشل مع اختلاط أنواع القيم (G).

## Q4: قواعد الأمان في 0.2

**التوصية:** اللغة كاملة عدا النادر:
- لا ندعم `getPriority()` و`auth.provider`، ونؤجل `query.*`.
- القاعدة التي تستعمل شيئًا غير مدعوم تُرفض عند الحفظ بخطأ 400، ولا تمنع بصمت.

**الدليل:**
- **حجم اللغة:** صغيرة، نحو 40 عنصرًا في صفحة مرجع واحدة (H).
  - أربعة أنواع قواعد: `.read` و`.write` و`.validate` و`.indexOn`.
  - المتغيرات: `auth` و`$` و`now` و`root` و`data` و`newData` و`query`.
  - 11 دالة للقطة، و7 للنص، و17 عملية.
- **ما يُستعمل فعلًا:** عيّنة من 2255 ملف `database.rules.json` في 2227 مستودعًا على GitHub (H):

  | الميزة | نسبة الملفات |
  |---|---|
  | `auth != null` | 75% |
  | `auth.uid === $var` | 63% |
  | `.validate` | 52% |
  | `hasChild` أو `hasChildren` | 44% |
  | `root.child` | 38% |
  | `.indexOn` | 35% |
  | `now` | 15% |
  | `auth.token.*` | 15% |
  | regex | 14% |
  | دوال نص أخرى | 6% |
  | `query.*` | 3% |
  | `getPriority` | 0.1% |

  - إسقاط regex ودوال النص و`query.*` معًا يكسر نحو 28% من الملفات.
  - العيّنة تميل إلى المشاريع التعليمية، فالنسب تقريبية.
- **الكلفة:** targaryen 4.4 ألف سطر JS، وقواعد Lark نحو 4.5 ألف سطر Rust. تقديرنا 3 إلى 4.5 ألف سطر Go. والصعب قراءة `root.child(...)` من Postgres أثناء الكتابة، لا اللغة نفسها.
- **الاختبار:**
  - حالات targaryen الـ 186 تغطي التعابير وحدها.
  - التسلسل (cascade) و`.validate` على الأبناء المكتوبين يُختبران بإطارات من المحاكي، وبمواصفات targaryen الأخرى.
- **regex:** ليست صيغة JS. `^` في البداية فقط، و`$` في النهاية فقط، والعلامة `i` وحدها، وبلا lookaround. فتكفي `regexp` في Go مع فحص عند الحفظ.

**ما يعنيه للجدول:** القواعد تنتقل من 0.3 إلى 0.2، لأن قاعدة بيانات بلا قواعد حقيقية لا تصلح لتطبيق حقيقي، و75% من التطبيقات تبدأ بـ `auth != null`.

## Q5: REST

**التوصية:** في 0.2:
- `GET` و`PUT` و`POST` و`PATCH` و`DELETE` على `/<path>.json`.
- `print=silent`، و`shallow`، ومعاملات الاستعلام.
- ETag و`If-Match` (412) و`If-None-Match` (304).
- `auth_variable_override`، والرمز في ترويسة `Authorization: Bearer`.
- `GET` و`PUT /.settings/rules.json`، ومعه `dryRun`.

ويؤجَّل البث (`text/event-stream`).

**الدليل (H، من الكود):**

| المكتبة | الطريقة |
|---|---|
| Admin Node وAdmin Java | WebSocket |
| Admin Go وAdmin Python | REST |
| Admin .NET | لا تحوي قاعدة بيانات |

- Node يستعمل REST لقراءة القواعد وكتابتها. والمعاملات في Go وPython تقوم على ETag و`If-Match`.
- **البث** يحتاجه `listen()` في Admin Python، و`database:profile` في أداة `firebase`. لا غيرهما.
- مكتبات التحقق المعتمدة هي Node وGo (ADR-016)، فيؤجَّل البث ويُوثَّق.
- **أداة `firebase`:** `database:get/set/update/push/remove` و`deploy` كلها REST عادي.

## Q6: الاستطلاع الطويل `/.lp`

**التوصية المحدّثة:** نبني `/.lp` في 0.2. كانت التوصية السابقة «لا»، وتغيّرت بعد قراءة كود مكتبة الويب.

**تأكد في متصفح حقيقي (J):** Chromium مع firebase 12.19.0 والمحاكي الرسمي خلف وكيل يرد على `/.lp` بـ 404.
- إعادة تشغيل 10 ثوانٍ لم يعد بعدها الاتصال خلال 120 ثانية، ولا بعد إعادة تحميل الصفحة.
- المتصفح بلا `localStorage` لم يتصل أصلًا.
- ومع `/.lp` عاد الاتصال بعد 2.1 ثانية.
- و`forceWebSockets()` يتجنب المشكلة، لكنه سطر إضافي.

**الدليل من الكود ✔ (firebase-js-sdk، الـ commit `d7bb0e16f2`):**
1. **قبل كل فتح لـ WebSocket تكتب المكتبة علامة فشل:** `localStorage['firebase:previous_websocket_failure'] = true`، والتعليق في الكود: «Assume failure until proven otherwise» (`WebSocketConnection.ts:160-162`).
2. **العلامة لا تُمسح إلا** حين يصير اتصال WebSocket سليمًا (`markConnectionHealthy`، `:288-290`). وفي الاستطلاع الطويل هذه الدالة فارغة (`BrowserPollConnection.ts:291`).
3. **إن وُجدت العلامة** يبدأ الاتصال التالي بالاستطلاع الطويل، ولا ينتقل إلى WebSocket إلا بعد نجاح مصافحة الاستطلاع (`TransportManager.ts:56-80`، و`Connection.ts:383-411`).
4. **إن لم يتوفر `localStorage`** (إطار معزول، أو تخزين محجوب) تعدّ المكتبة WebSocket فاشلًا دائمًا (`:279-286`).

**النتيجة المتوقعة بلا `/.lp`:**
- أي إعادة تشغيل للخادم، أو انقطاع أثناء فتح WebSocket، يترك العلامة.
- بعدها يحاول متصفح المستخدم `/.lp` فيجد 404، فلا يعود إلى WebSocket أبدًا، حتى بعد إعادة تحميل الصفحة، لأن العلامة في `localStorage`.
- Android وiOS وNode لا يتأثرون، فلا كود استطلاع فيها.

**الحل المؤقت للمطوّر:** `forceWebSockets()`، أو `databaseURL` يبدأ بـ `wss://`. لكن هذا سطر إضافي، يخالف وعد «ملف الإعداد وحده».

## Q7: سجل الأحداث المشترك

**التوصية:** كتابات RTDB لا تدخل `events.changes`.
- لكل قاعدة رقم ترتيب في صفها في `rtdb.databases`، يزيده الكاتب في معاملة الكتابة نفسها.
- السجل المشترك يبقى لأحداث الخدمات، كإنشاء مستخدم.

**الدليل:**
- رقم `IDENTITY` في `events.changes` يُعطى قبل اكتمال الحفظ، فقارئ يتقدم بالرقم قد يفوته تغيير من معاملة اكتملت متأخرة (D: Dudycz وGrittner). والكاتب الواحد يزيل المشكلة من أصلها.
- وأداة قياس الأداء في Firebase تتحدث عن «pending time» و«head-of-line blocking» لكل قاعدة، وهذا يوافق كاتبًا مرتّبًا واحدًا لكل قاعدة (E). هذا استنتاج، لا تصريح.
- ورسائل الدردشة ستضخم السجل المشترك بلا فائدة لقارئيه.
