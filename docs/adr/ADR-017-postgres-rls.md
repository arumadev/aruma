# ADR-017: العزل بين المشاريع داخل Postgres (RLS)

- الحالة: معتمد (تأجيل)
- التاريخ: 2026-10-20
- المرحلة: بين الإصدار 0.1 (Auth) وRealtime Database (القرار F5)
- المراجع: ADR-009، ADR-015

## السياق

كل بيانات المشاريع في قاعدة Postgres واحدة، وكل جدول فيه رقم المشروع. والخطر: استعلام ينسى شرط المشروع فيقرأ بيانات مشروع آخر أو يغيّرها.

Row-Level Security (RLS) في Postgres حاجز ثانٍ داخل القاعدة نفسها: يرفض أي صف لا يخص المشروع المضبوط في الجلسة، حتى لو أخطأ الكود.

ما يحمي اليوم:
- **فحص آلي لكل استعلام** (`internal/store/scopecheck`): كل استعلام في `queries/*.sql` يمس صفوف مشروع يقيّد بـ `project_number`، أو يعلن نطاقه صراحة (`-- scope: global` أو `-- scope: owner`) مع سببه.
- **اختبارات عزل** في `test/acceptance/isolation_test.go` في كل تشغيل CI: المالك لا يصل إلى مشروع غيره، ولا رمز حساب خدمة، ولا ملف إعداد، ولا نقل لموارد بين المشاريع.
- **المراجعة الأمنية v0.1** فحصت العزل عبر Admin API والكونسول ورموز حسابات الخدمة، ولم تجد ثغرة.

## القرار

**نؤجّل RLS.** لا نضيفه قبل Realtime Database. نعيد النظر في ثلاث حالات:
- خدمة تكتب استعلامات تُبنى وقت التشغيل، فلا يراها الفحص الآلي (قد يحدث مع استعلامات Firestore).
- أول ثغرة عزل تظهر رغم الفحص والاختبارات.
- تشغيل متعدد المستأجرين لجهات لا تثق ببعضها على قاعدة واحدة.

## البدائل المرفوضة

- **RLS الآن:**
  - يحتاج ضبط المشروع في كل اتصال (`SET LOCAL` داخل كل معاملة) عبر مجمّع الاتصالات.
  - ويغيّر كل migration صدر بسياسات جديدة، ويبطئ الاستعلامات العامة المشروعة (التنظيف الدوري) التي تحتاج دورًا يتجاوزه.
  - والحماية التي يضيفها مغطّاة اليوم بالفحص والاختبارات.

## العواقب

- العزل يبقى مسؤولية الكود والفحص الآلي. لذلك يبقى `scopecheck` إلزاميًا لكل خدمة جديدة، ولكل خدمة اختبارات عزل خاصة بها.
- إن أضفنا RLS لاحقًا يأتي في migration جديد (ADR-015: الـ migrations الصادرة لا تُعدَّل).
