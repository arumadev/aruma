# ADR-019: تخزين Realtime Database وترتيب الكتابة وحدودها

- الحالة: معتمد
- التاريخ: 2026-10-20
- المرحلة: R0 من Realtime Database (الإصدار 0.2)
- المراجع: [rtdb-decisions.md](../research/rtdb-decisions.md) (Q2 وQ7 وQ8)، [rtdb/G-storage-bench.md](../research/rtdb/G-storage-bench.md)، [rtdb/D-articles-design.md](../research/rtdb/D-articles-design.md)، ADR-009، ADR-015

## السياق

- **ما يشترطه البروتوكول:**
  - كل المستمعين يرون الكتابات بترتيب واحد.
  - دفعة البيانات تصل قبل تأكيد الكتابة لصاحبها.
  - المعاملة تُرفض بـ `datastale` إن تغيّرت القيمة.
- **ما تمنعه Postgres:** رقم التسلسل فيها يُعطى قبل اكتمال الحفظ. فمن يقرأ التغييرات بالرقم من كتّاب متزامنين قد يفوته تغيير.
- **ما قسناه:** قارنّا أربعة نماذج تخزين على 600 ألف ورقة (G).

## القرار

1. **التخزين: صف لكل ورقة.** المخطط `rtdb`:
   - `rtdb.databases`: قاعدة لكل مشروع في 0.2. الاسم، والقواعد، و`seq` (رقم آخر كتابة مطبّقة)، وأوقات الإنشاء والتعديل.
   - `rtdb.nodes(database_id, path text COLLATE "C", value jsonb, priority jsonb, PRIMARY KEY (database_id, path))`.
     - قراءة الفرع `p`: صفه هو، ثم نطاق `path >= p||'/' AND path < p||'0'`.
     - ترتيب الأبناء يُحسب في Go بقواعد Firebase، لا بترتيب النص.
   - القيم الداخلية (الكائنات) لا تُخزَّن، تُستنتج من الأوراق. والأولوية على كائن تُخزَّن في صف خاص بالمسار نفسه، مع علامة أنه ليس ورقة.
2. **الكاتب: ممثل واحد لكل قاعدة.**
   - goroutine تملك صندوقًا واردًا، وتطبّق الأوامر بترتيب وصولها.
   - تجمع حتى N أمر في معاملة Postgres واحدة.
   - تزيد `seq` في المعاملة نفسها.
   - **بعد اكتمال الحفظ فقط** ترسل الدفعات للمستمعين، ثم التأكيد لصاحب الكتابة.
   - القواعد وقيم الخادم والبصمة تُحسب داخل الكاتب، على الحالة التي سيكتب فوقها.
3. **التوزيع داخل العملية.**
   - شجرة مستمعين في الذاكرة لكل قاعدة.
   - لا LISTEN/NOTIFY، ولا قراءة تغييرات من Postgres، ولا logical replication.
   - خادم واحد في 0.2. وتعدد الخوادم لاحقًا: الكاتب لكل قاعدة يصير عقدًا واحدًا يحمل قفل قيادة (advisory lock)، ويُكتب له ADR عند الحاجة.
4. **سجل الأحداث المشترك:** كتابات RTDB لا تدخل `events.changes`.
5. **الحدود الافتراضية:**

   | الحد | القيمة |
   |---|---|
   | طول المسار، بكل أجزائه | 768 بايت |
   | العمق | 32 |
   | النص الواحد | 10 MB |
   | رسالة WebSocket المجمّعة، والكتابة من المكتبة | 16 MB |
   | الكتابة عبر REST | 16 MB، قابلة للرفع (Firebase: 256 MB) |
   | الكتابة في الدقيقة لكل قاعدة | 64 MB |
   | الاتصالات لكل مشروع | 10 آلاف |
   | طابور الخروج لكل اتصال | 64 MB. وإذا امتلأ يُغلق الاتصال، والعميل يعيد المزامنة وحده |

   - كلها قابلة للضبط في قسم `rtdb` من الإعداد.
   - ومسارات RTDB مستثناة من حد الجسم العام (1 MB)، ومن مهلتي القراءة والكتابة (60 ثانية) للاتصال المرقّى.

## البدائل المرفوضة

- **jsonb لكل فرع:**
  - نحو 740 كتابة في الثانية لكل غرفة، أي دون حد Firebase.
  - وكتابتان فقط في الثانية لكل فرع رئيسي.
  - ويتضخم: 469 و612 MB بعد التجربة.
- **شجرة في الذاكرة مع سجل:**
  - أسرع في القراءة الكبيرة.
  - لكنها تحتاج لقطات وضغطًا: إعادة تشغيل 3.8 مليون سطر أخذت 8.5 ثوانٍ.
  - وتحدّ القاعدة بالذاكرة، نحو 184 بايت لكل ورقة.
  - تبقى خيارًا ذاكرةً مؤقتةً فوق Postgres إن أظهر قياس R7 الحاجة.
- **ltree:** لا يقبل أحرف مفاتيح RTDB.
- **LISTEN/NOTIFY:**
  - حمولته أقل من 8000 بايت.
  - ويأخذ قفلًا عامًا عند الاكتمال، وسبّب انقطاعات موثّقة.
  - ولا حاجة إليه ما دام خادم واحد يملك الكتابة.
- **رقم `events.changes` مع كتّاب متزامنين:** يفوّت تغييرات (Dudycz، وGrittner).

## العواقب

- **صاحب الكتابة يرى ترتيب Firebase نفسه:** البيانات قبل التأكيد، والاستماع قبل تأكيده.
- **قاعدة مزدحمة لا تؤخّر غيرها،** لأن لكل قاعدة كاتبها. لكن داخل القاعدة الواحدة كل الكتابات متتابعة، كما في Firebase.
- **قراءة فرع ضخم دفعة واحدة مكلفة:** 107 ms لخمسين ألف ابن. تُقاس في R7.
- **إعادة تشغيل الخادم لا تحتاج استرجاع حالة،** فالعملاء يعيدون الاستماع ببصمة ما عندهم.
- **أوامر onDisconnect عند الإيقاف:**
  - **الإيقاف المنظَّم:** ينفّذ أوامر كل اتصال عبر كاتبها قبل الإغلاق، كأن الاتصالات انقطعت.
  - **الانهيار المفاجئ:** يفقدها، لأنها في الذاكرة. والعميل يسجّلها من جديد عند إعادة الاتصال، فهذا سلوك المكتبات.
  - يُوثَّق هذا الفرق في `docs/compat`.
